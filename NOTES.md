## Исследование API Telegram (05.11, по просьбе владельца «нужен свой API»)
- Мы уже работаем через внутренний API Telegram (MTProto, слой 229 — тот же, что у официальных приложений: 823 метода, 1697 типов).
- Аналогия с «неофициальным API Яндекс Музыки» не работает: там повторяют возможности приложения, а приложения Telegram сами не умеют искать розыгрыши глобально — скрытой функции нет.
- Методы про розыгрыши: `payments.getGiveawayInfo` (по известному посту), бусты (`premium.getBoostsStatus/List` — только для админов своего канала), подарочные коды, запуск своего розыгрыша. Поиска среди них нет.
- Фильтров поиска сообщений 18 (фото, видео, ссылки, опросы…), фильтра «розыгрыш» нет. Глобальные поиски (`messages.searchGlobal`, `channels.searchPosts`, `contacts.search`) — только по тексту/названиям.
- Telegram Web (исходники `morethanwords/tweb`, `Ajaxy/telegram-tt`) — тот же клиент на том же API (MTProto через WebSocket, как наш бот из облака), своей базы нет. Про розыгрыши он вызывает только `payments.getGiveawayInfo` (клик по розыгрышу в открытом чате) и методы запуска своего розыгрыша; розыгрыши видит лишь как сообщения в открытых чатах.
- Готовые базы розыгрышей есть только у сторонних: telegramgiveaways.ru (= канал @giveaways_database, уже наш источник №1), TGStat/Telemetr (платные API).
- Идея владельца «соединить поиск Telegram с меткой» **проверена 05.11**: поиск по 11 хэштегам нашёл текстовые посты про розыгрыши в 1968 каналах; в 250 из них проверены соседние сообщения (±4 от каждого поста) — **0** официальных розыгрышей по метке. Хэштеги/текст ведут к обычным конкурсам, официальные розыгрыши публикуют отдельно, без текста. Скрипт: `scratchpad/search_neighbors.py`.

## Правила публикаций (согласованы с владельцем)
- **1 пост раз в 3,5 часа.** Ищем **с запасом**: один поиск (перебор каналов) набирает до 10 подходящих розыгрышей; каждые 3,5 часа публикуем из запаса тот, что **раньше закончится** (при равенстве — «для всех стран»). Когда запас кончился — ищем снова. Ведём учёт опубликованного, чтобы **не повторяться**. Сразу много не постить. (Решение владельца 05.11; до этого было «искать по одному».)
- Только **официальные** розыгрыши (`messageMediaGiveaway`), только **не завершённые**: до конца должно оставаться не меньше 3 часов.
- **Приз — любой** («давай все подряд», владелец 05.11 днём): порогов по звёздам и подпискам нет. История: было 10 000 ⭐ / Premium от 5 → 5 000 / от 3 → без порогов.
- **Иностранные каналы тоже ищем** (владелец 05.11): там бывают розыгрыши «для всех стран». Добавлены международные слова и хэштеги (EN, ES, PT, TR, UA, FA, AR). Фильтр по странам остаётся: все / РФ / РБ / КЗ.
- Страны: **все / РФ / РБ / КЗ**, «для всех стран» в приоритете; розыгрыши для других стран не берём.
- Поиск — **перебором каналов через API** (так и объяснять владельцу).
- **@razdacha_TelegramPremium** — источник владельца (почти только официальные розыгрыши), проверяется первым.
- Идея владельца (05.11): стартовые каналы (агрегаторы, свой список) читаем на **500 последних записей** без ограничения по дате (`--source-limit 500`) и проверяем каналы организаторов **в том числе закончившихся** розыгрышей и итогов — они могли запустить новый и не скинуть его в агрегатор. Проверка на @razdacha_TelegramPremium: 248 каналов, 10 подходящих, из них новые — Premium 3 мес × 3 (@airdropinspector) и два по 10 000 ⭐ × 100 из закрытых каналов. Повторно запущенный розыгрыш (новая дата окончания) считается новым и может быть опубликован.
- Пересылать **только напрямую из публичного канала-организатора** (первый канал в списке розыгрыша, у него есть @username). Копии из агрегаторов и других каналов **не берём**, даже если организатор закрыт. Закрытый организатор — розыгрыш пропускаем (подтверждено владельцем 05.11).
- Розыгрыши из **закрытых** каналов (или с запретом пересылки) переслать нельзя: они запоминаются как непригодные (`bad`), и поиск продолжается, до 3 попыток за запуск.
- Не дублировать то, что уже есть в канале, кто бы это ни опубликовал.
- После **любого** поста владельца (кроме служебных) выдерживать **5 часов**; его отложенные посты тоже учитываются.

## Как устроено (GitHub)
- `.github/workflows/repost.yml` запускается каждые 30 минут и **просто обновляется** (проверяет время и посты владельца). **Публиковать — только раз в 3,5 часа**: берём из запаса тот, что раньше закончится, публикуем, записываем в учёт; искать (до 10 в запас, `--reserve 10`) — только когда запас кончился (`--schedule-ahead 0`). Отложенные посты заранее НЕ ставим: владелец просил простую схему.
- GitHub пропускает запуски по расписанию (в ночь на 05.11 сработал 1 из 15). Поэтому ежечасная проверка ассистента запускает задание вручную, если давно не было запуска.
- Ошибка 05.11 (2): запуск в 08:38 UTC пропустил пост, т.к. до срока было 4 минуты (допуск был 2 мин), а следующего запуска GitHub не сделал → пост опоздал. Исправлено: допуск 10 минут, публикация сразу.
- Ошибка 05.11, не повторять: я усложнил схему отложенными постами, и поиск запускался не раз в 3,5 ч. Владелец недоволен — делать ровно как сказано.
- Вне очереди (по просьбе владельца): Actions → «Репост розыгрышей» → Run workflow, в поле `post_now` ссылка на розыгрыш из запаса. Пересылается сразу, обычное расписание 3,5 ч не сдвигается. 05.11 так опубликован otdel34/382.
- Учёт (что опубликовано, очередь, отложенный пост, время постов) хранится в кэше Actions, начальное состояние лежит в `state/`.
- Секреты репозитория: `TG_API_ID`, `TG_API_HASH`, `TG_STRING_SESSION`. Строку сессии при копировании с телефона портят пробелы и переносы: скрипт их вычищает.
- `keepalive.yml`: раз в 55 дней служебный коммит (буква в `.github/keepalive`), чтобы GitHub не отключил расписание.
- Репозиторий публичный: минуты Actions бесплатны, секреты защищены.
