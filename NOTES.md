## Как ищем розыгрыши (объяснять владельцу именно так)
- Розыгрыш определяем **только по типу сообщения** `messageMediaGiveaway` (официальный розыгрыш Telegram). Текст и хэштеги розыгрышем не считаются.
- Глобального поиска по типу сообщения у Telegram нет. Поэтому сначала выбираем, **какие каналы открыть**: свой список (`state/sources.txt`), агрегаторы, каналы-организаторы из найденных розыгрышей, а если там пусто — каналы из поиска по словам и хэштегам. Внутри каждого канала проверяем **тип каждого сообщения**.
- Хэштеги и слова нужны только чтобы находить каналы, а не розыгрыши. Не говорить владельцу «искал по хэштегам»: это его злит и звучит неверно.
- Проверено 05.11: глобальный поиск по хэштегам (`channels.searchPosts`, 200 постов) вернул **0** сообщений-розыгрышей — посты-розыгрыши без текста в этот поиск не попадают. Полнотекстовый глобальный поиск требует **Premium** (у Dolli его нет, ошибка `PremiumAccountRequiredError`). **Проверено с Premium (05.11, владелец дал Premium на Dolli):** полнотекстовый глобальный поиск по запросам «Telegram Premium», «Stars», «розыгрыш», «giveaway» вернул 400 постов и **0** сообщений-розыгрышей по типу. Telegram не индексирует розыгрыши в глобальном поиске, искать их напрямую по всему Telegram нельзя. Квота поиска с Premium — всего 10 запросов в сутки. Вывод окончательный: единственный рабочий способ — открывать каналы и проверять тип сообщений.
- Статистика на 05.11: просмотрено 676 каналов, в них 26 активных официальных розыгрышей. Почти все — в агрегаторах (@rozygrysh, @rozygrysh3, @ChannelGiveaways…) и у их организаторов.

## Исследование API Telegram (05.11, по просьбе владельца «нужен свой API»)
- Мы уже работаем через внутренний API Telegram (MTProto, слой 229 — тот же, что у официальных приложений: 823 метода, 1697 типов).
- Аналогия с «неофициальным API Яндекс Музыки» не работает: там повторяют возможности приложения, а приложения Telegram сами не умеют искать розыгрыши глобально — скрытой функции нет.
- Методы про розыгрыши: `payments.getGiveawayInfo` (по известному посту), бусты (`premium.getBoostsStatus/List` — только для админов своего канала), подарочные коды, запуск своего розыгрыша. Поиска среди них нет.
- Фильтров поиска сообщений 18 (фото, видео, ссылки, опросы…), фильтра «розыгрыш» нет. Глобальные поиски (`messages.searchGlobal`, `channels.searchPosts`, `contacts.search`) — только по тексту/названиям.
- Вывод: «свой API» = **собственный индекс розыгрышей** (как TGStat): растущий реестр каналов + почасовой инкрементальный обход (только новые посты, 1 запрос на канал) + база розыгрышей + выдача из базы. Предложено владельцу, ждём «начинаю».

## Правила публикаций (согласованы с владельцем)
- **1 пост раз в 3,5 часа.** Ищем **с запасом**: один поиск (перебор каналов) набирает до 10 подходящих розыгрышей; каждые 3,5 часа публикуем из запаса тот, что **раньше закончится** (при равенстве — «для всех стран»). Когда запас кончился — ищем снова. Ведём учёт опубликованного, чтобы **не повторяться**. Сразу много не постить. (Решение владельца 05.11; до этого было «искать по одному».)
- Только **официальные** розыгрыши (`messageMediaGiveaway`), только **не завершённые**: до конца должно оставаться не меньше 3 часов.
- **Stars от 5 000** звёзд на весь розыгрыш, **Premium от 3** подписок (снижено владельцем 05.11; раньше было 10 000 / 5: подходящих находилось слишком мало).
- Страны: **все / РФ / РБ / КЗ**, «для всех стран» в приоритете; розыгрыши для других стран не берём.
- Поиск — **перебором каналов через API** (так и объяснять владельцу).
- **@razdacha_TelegramPremium** — источник владельца (почти только официальные розыгрыши), проверяется первым.
- Идея владельца (05.11): стартовые каналы (агрегаторы, свой список) читаем на **500 последних записей** без ограничения по дате (`--source-limit 500`) и проверяем каналы организаторов **в том числе закончившихся** розыгрышей и итогов — они могли запустить новый и не скинуть его в агрегатор. Проверка на @razdacha_TelegramPremium: 248 каналов, 10 подходящих, из них новые — Premium 3 мес × 3 (@airdropinspector) и два по 10 000 ⭐ × 100 из закрытых каналов. Повторно запущенный розыгрыш (новая дата окончания) считается новым и может быть опубликован.
- Пересылать **только напрямую из публичного канала-организатора** (первый канал в списке розыгрыша, у него есть @username). Копии из агрегаторов и других каналов **не берём**, даже если организатор закрыт. Закрытый организатор — розыгрыш пропускаем (подтверждено владельцем 05.11).
- Розыгрыши из **закрытых** каналов (или с запретом пересылки) переслать нельзя: они запоминаются как непригодные (`bad`), и поиск продолжается, до 3 попыток за запуск.
- Не дублировать то, что уже есть в канале, кто бы это ни опубликовал.
- После **любого** поста владельца (кроме служебных) выдерживать **5 часов**; его отложенные посты тоже учитываются.

## Как устроено (GitHub)
- `.github/workflows/repost.yml` запускается каждые 30 минут и **просто обновляется** (проверяет время и посты владельца). **Публиковать — только раз в 3,5 часа**: берём из запаса тот, что раньше закончится, публикуем, записываем в учёт; искать (до 10 в запас, `--reserve 10`) — только когда запас кончился (`--schedule-ahead 0`). Отложенные посты заранее НЕ ставим: владелец просил простую схему.
- GitHub пропускает запуски по расписанию (в ночь на 05.11 сработал 1 из 15). Поэтому ежечасная проверка ассистента запускает задание вручную, если давно не было запуска.
- Ошибка 05.11, не повторять: я усложнил схему отложенными постами, и поиск запускался не раз в 3,5 ч. Владелец недоволен — делать ровно как сказано.
- Учёт (что опубликовано, очередь, отложенный пост, время постов) хранится в кэше Actions, начальное состояние лежит в `state/`.
- Секреты репозитория: `TG_API_ID`, `TG_API_HASH`, `TG_STRING_SESSION`. Строку сессии при копировании с телефона портят пробелы и переносы: скрипт их вычищает.
- `keepalive.yml`: раз в 55 дней служебный коммит (буква в `.github/keepalive`), чтобы GitHub не отключил расписание.
- Репозиторий публичный: минуты Actions бесплатны, секреты защищены.

## Общение с владельцем
- Отвечать коротко и по делу. Делать ровно то, что он сказал, без лишних усложнений. Не переспрашивать то, что он уже сказал (перечитать этот файл).
- Писать ему **в Telegram**, а не в чат Claude. В чат Claude **не пересказывать** переписку из Telegram.
- Владельцу отвечать **сразу**, без пауз и долгого «печатает».
- Просьбы опубликовать розыгрыш, пришедшие на Dolli от других людей, **пересылать владельцу**.
- Связь проверяется **раз в час** (минимальный интервал запланированных задач платформы — 1 час; 30 минут она не принимает). Длинные фоновые процессы в облачной сессии Claude ограничены 2 часами, и платформа просит не перезапускать их бесконечно. Поэтому проверка — короткий разовый запуск: `scratchpad/owner_chat.py check` / `send "текст"`.

## Взаимный пиар (ВП)
- **Не начинать, пока в канале меньше 1000 подписчиков** (на 05.11 их 15).
- Затем 1–2 предложения за 4 дня, только админам, у которых в описании канала указан контакт для рекламы или ВП. В первом сообщении сразу называть их канал.
- С собеседниками: разные паузы перед ответом (8–20 с, 1–3 мин, иногда 6–12 мин), «печатает», короткие и средние сообщения. Ночью (00:00–07:00 по Минску) им не отвечать.
- Самому соглашаться только на обмен постами 1 на 1 и время. Деньги, закреп и прочее — сначала спросить владельца.
- На прямой вопрос «ты бот?» не врать и не уходить от ответа: остановиться и передать разговор владельцу.
- Накрутку подписчиков и массовые рассылки не делаем (отказано: риск бана Dolli, на нём держится автопостинг).

## Технические выводы
- Из облачной среды Claude прямой TCP к Telegram закрыт. Работает только WebSocket через `*.web.telegram.org` (5 доменов разрешены в настройках сети среды; `TG_TRANSPORT=ws` включается сам при `HTTPS_PROXY`).
- Код входа Telegram на серверный вход из дата-центра **не приходит**: входить по QR-коду (живёт ~30 с, присылать картинкой сразу).
- Сессия Telegram в облачной сессии Claude хранится в scratchpad и может пропасть при пересоздании контейнера. Тогда нужен новый вход по QR. На GitHub своя копия в секрете.
- Не делать `logout` этой сессией: у GitHub тот же ключ авторизации, автопостинг остановится.
